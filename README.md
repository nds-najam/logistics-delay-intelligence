# DataQ | Logistics Delay Intelligence

A client-facing proof-of-concept analytics + machine-learning application built for a logistics
company whose primary pain point is **delayed packages**. Runs entirely locally on synthetic data --
no cloud services, no external APIs.

> Predictions indicate risk based on historical patterns and should support, not replace, operational
> decision-making.

## 1. Project Objective

> Identify why packages are delayed, quantify the major causes, predict which packages are at risk of
> delay, and provide actionable recommendations to reduce delays.

The application walks a single narrative end to end:

```
DATA -> DATA QUALITY -> DELAY DETECTION -> ROOT CAUSE ANALYSIS -> DELAY PREDICTION
     -> EXPLANATION -> RECOMMENDATION -> WHAT-IF ANALYSIS -> OPERATIONAL ACTION
```

## 3. Dataset Description

`src/data_generator.py` produces >=100,000 shipment records (default 120,000, ~120,600 after
duplicate injection) with the columns requested in the brief: identifiers, origin/destination
geography, warehouse, carrier, service level, package attributes, dates, promised vs. actual
delivery, distance, five operational component-time columns (warehouse processing, pickup,
transit, sorting, last mile, customs), handoffs, weather, traffic, seasonality flags, driver /
vehicle availability, warehouse utilization, payment status, address quality, customer priority,
and the delay outcome fields (`Delay_Flag`, `Delay_Hours`, `Delay_Category`, `Delay_Reason`).

`Delay_Flag = 1` when `Actual_Delivery_Date > Expected_Delivery_Date`; `Delay_Hours` is the gap in
hours (0 for on-time shipments); `Delay_Category` attributes each delayed shipment to the largest
contributing operational component (Warehouse Processing, Pickup, Transit, Sorting, Customs, Last
Mile, Weather, Traffic, Address Issue, Capacity, Driver Availability, or Other), with `No Delay`
for on-time shipments.

## 4. How Synthetic Data Is Generated

The generator builds **causal, not random**, relationships, then adds controlled noise so the
downstream model has genuine signal to learn rather than a lookup table:

- Warehouse capacity utilization (with a per-warehouse structural baseline -- some sites run
  chronically hotter than others) drives warehouse processing time and sorting time.
- Traffic level drives last-mile and transit time; weather severity drives transit time.
- Number of handoffs (distance + customs + sea-freight driven) drives sorting time and delay odds.
- Poor address quality drives last-mile delay.
- Cross-region shipments incur a customs-clearance stage ~18% of the time.
- Peak season (Nov-Dec and a Ramadan-proxy Mar-Apr window) raises warehouse utilization and
  customs time.
- Low driver/vehicle availability (itself reduced by weekends, holidays, and heavy traffic) raises
  pickup and last-mile time.
- Distance and shipping mode set the physical floor on transit time; carrier risk multipliers and
  per-carrier pickup-speed effects create genuine carrier-to-carrier performance differences.
- **Service-tier speed matching:** faster service tiers (Same-Day, Express) get operationally
  prioritized handling (shorter processing/pickup/sorting/last-mile times) so their tight promise
  windows are achievable under normal conditions -- delay still emerges primarily from operational
  stressors rather than from a structural mismatch between promise and average operational time.

`_inject_data_quality_issues()` then adds, on the *raw* data only: missing values (~1-1.5% across
five columns), inconsistent categorical spellings (`road` / `ROAD` / `Road ` etc.), extreme
outliers in package weight and delay hours (applied only to already-delayed shipments, so an
on-time shipment can never end up with nonzero delay hours), and ~0.5% duplicate rows.

## 5. Data Quality

`src/data_processing.py` separates **assessment** (`assess_data_quality`, run on raw data -- record
count, missing values, duplicates, IQR-based outlier counts, inconsistent-spelling detection,
completeness %) from **cleaning** (`clean_pipeline` -- standardizes categorical spellings, drops
exact duplicates, imputes missing values (median for continuous, 0 for "not applicable" customs
time, mode for categorical), and winsorizes extreme outliers at the 99.5th percentile rather than
dropping rows). Both reports are surfaced on the **Data Quality** page. All other pages operate on
the cleaned data.

## 6. ML Methodology

**Target:** `Delay_Flag` (binary classification).

**Feature selection (important):** the five component "process time" columns (warehouse
processing, pickup delay, transit, sorting, last-mile, customs-clearance hours) are **deliberately
excluded** from the model's features. Those are only known *after* a shipment has largely
completed its journey -- including them would let the model trivially reconstruct the delay
outcome instead of genuinely predicting risk from information available at dispatch time. The
model uses 22 dispatch-time features: distance, handoffs, package weight/volume, warehouse
utilization, driver/vehicle availability, a derived cross-region flag (a legitimate proxy for
customs exposure, known before dispatch), and categorical/binary context (region, mode, carrier,
service type, package type, weather, traffic, address quality, customer priority, payment status,
holiday/weekend/peak-season flags).

**Models compared:** Logistic Regression, Random Forest, and HistGradientBoosting, each inside a
`ColumnTransformer` (standard-scaled numeric + one-hot categorical) `Pipeline`, trained on an 80/20
stratified split.

**Selection rule:** because a missed at-risk shipment (false negative) costs the business a
customer who experiences the delay with zero chance of intervention, while a false alarm only
costs a wasted review, the model is selected primarily on **recall for the delayed class** --
gated by a minimum precision floor (to rule out a degenerate "always predict delayed" model) --
with ROC-AUC and F1 reported for full transparency on the Delay Prediction page. Class imbalance
is handled via `class_weight="balanced"` (or `sample_weight` for HistGradientBoosting, which has no
native `class_weight`).

**Risk tiers:** LOW (<25%), MEDIUM (25-50%), HIGH (50-75%), CRITICAL (>=75%) predicted probability.
**Estimated delay hours** per shipment is the historical average `Delay_Hours` for shipments that
fell in the same risk tier on the held-out test set (a calibration lookup, not a second regression
model -- kept intentionally simple and defensible rather than overclaiming precision).

## 7. Root Cause Methodology

`src/delay_analysis.py` is pure analysis (no ML): delay-by-cause aggregation, segment
decomposition (compare any Carrier / Region / Warehouse / Mode / Service-Type value against the
network), Pearson correlation of operational drivers against `Delay_Flag`, quantile-bucketed delay
rates, and route/warehouse/carrier rollups (carrier rankings require a minimum volume so a
low-sample carrier can't look artificially bad or good). All wording uses "associated with," never
"causes," since this is observational correlation, not a designed experiment.

## 8. Recommendation Methodology

`src/recommendations.py` re-runs the same segment analysis and turns any finding that clears a
materiality threshold (delay rate meaningfully above the network average) into a card with
**Issue / Evidence / Recommended Action / Expected Impact / Priority** (HIGH/MEDIUM/LOW by ratio
to the network average). Expected impact is always phrased as an estimate tied to closing the gap
to the network average -- never a fabricated dollar figure. A parallel, lighter-weight function
maps a single shipment's top explainability factors to a concrete suggested action for the
Shipment Risk page.

## 9. Installation

```bash
python3 -m venv .venv
source .venv/bin/activate        # or .venv\Scripts\activate on Windows
pip install -r requirements.txt
```

> If your project directory lives on a slow/virtualized filesystem (e.g. a Windows drive mounted
> into WSL2), create the venv on native Linux storage instead and symlink it in -- this avoided a
> 15+ minute install becoming a few seconds in development.

## 10. How to Run

```bash
streamlit run app.py
```

On first run, if `data/synthetic_logistics_data.csv` or `models/delay_risk_model.joblib` don't
exist yet, the app generates the dataset and trains/saves the model automatically (a one-time
~30-60 second wait, cached afterward via `st.cache_data` / `st.cache_resource` and the on-disk
model file).

To regenerate the dataset or retrain the model directly:

```bash
python -c "import sys; sys.path.insert(0,'src'); from data_generator import generate_dataset; generate_dataset(120_000).to_csv('data/synthetic_logistics_data.csv', index=False)"
python -c "import sys; sys.path.insert(0,'src'); import data_processing as dp, model as mdl; df,_,_ = dp.load_and_clean(); b = mdl.train_and_select(df); mdl.save_model(b)"
```

Run the test suite:

```bash
pytest tests/ -v
```

## 11. Application Pages

Sidebar filters (date range, region, origin/destination city, carrier, shipping mode, service
type, warehouse, delay category, customer priority, weather) apply reactively to every analytics
page. The Delay Prediction, Shipment Risk, What-If, and Model Governance pages use the model
trained once on the full historical dataset (retraining per filter change would be impractical and
would not reflect what a production model would actually be trained on).

1. **Executive Overview** -- KPI cards, volume/delay-rate trends, on-time split, delay-hours
   distribution, dynamically generated Key Insights.
2. **Root Cause Analysis** -- delay-by-cause charts + top contributors, segment decomposition,
   driver analysis (correlation, box plots, delay-rate-by-bucket).
3. **Delay Prediction** -- model comparison table, confusion matrix, permutation-importance global
   feature importance, optional supplementary SHAP summary, recall-first selection rationale.
4. **Shipment Risk** -- select an existing shipment or enter one manually; delay probability, risk
   tier, estimated delay hours, top contributing factors, recommended actions.
5. **Recommendations** -- prioritized Issue/Evidence/Action/Impact cards.
6. **What-If Analysis** -- adjust operational parameters on a base shipment and see the model's
   probability response (explicitly labeled a model-based scenario).
7. **Route Analytics**, 8. **Warehouse Analytics**, 9. **Carrier Analytics** -- volume-aware
   performance rollups with worst-performer views.
10. **Business Impact** -- delayed shipments, total delay hours, estimated SLA breaches / customers
    affected, adjustable cost-per-delay assumption.
11. **Operational Alerts** -- auto-detected warehouse/carrier/route anomalies + DataQ Intelligent
    Insights (all programmatic, no external LLM).
12. **Data Quality** -- raw DQ report + what the cleaning pipeline fixed.
13. **Model Governance** -- model provenance, training details, metrics, feature list, limitations,
    and the standing disclaimer.

## 12. Assumptions

- Cost per delayed shipment defaults to $75 (adjustable on the Business Impact page) -- an
  illustrative placeholder, not a real cost model.
- SLA breach threshold defaults to 24 hours of delay.
- Risk-tier thresholds (25/50/75%) and the minimum-volume floors used for "fair ranking" (carriers)
  and alerting (warehouses/routes/carriers) are reasonable defaults set for this proof-of-concept,
  not calibrated against a real operational cost function.
- All data is synthetic; city/region names are illustrative, not a real service network.

## 13. Limitations

- Synthetic data encodes the causal relationships described above; real operational data will have
  its own (likely messier, more confounded) structure.
- The model captures statistical association learned from historical patterns, not a mechanistic
  or causal model of logistics operations -- language throughout the app reflects this.
- Estimated delay hours per risk tier is a historical-average lookup, not a dedicated regression
  model, and should be read as a rough magnitude.
- Financial figures are explicit, adjustable assumptions, not derived from real cost data.

## 14. Future Enhancements
